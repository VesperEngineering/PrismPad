# PrismPad v0.1.0 Release Design

## Goal

Publish PrismPad v0.1.0 as the first public GitHub release from the tested
`main` branch. The release must contain installable Windows and Ubuntu packages
and must not be created unless every required validation succeeds.

## Release identity

- Version: `0.1.0`
- Git tag: `v0.1.0`
- Release title: `PrismPad v0.1.0`
- Target: the exact `main` commit containing the approved release workflow
- Status: stable, not a prerelease
- Signing: unsigned until a Vesper Applied LLC Authenticode certificate is
  configured

The package manifests already identify version `0.1.0`. The workflow must fail
if `package.json`, `src-tauri/Cargo.toml`, and
`src-tauri/tauri.conf.json` do not all match the release tag.

## Published assets

The release will contain exactly these four platform packages:

- Windows 10/11 x64 portable executable:
  `PrismPad-v0.1.0-windows-x64-portable.exe`
- Windows 10/11 x64 NSIS installer:
  `PrismPad-v0.1.0-windows-x64-setup.exe`
- Linux x64 portable AppImage: `PrismPad-v0.1.0-linux-x64.AppImage`
- Ubuntu 24.04+ x64 Debian package:
  `PrismPad-v0.1.0-ubuntu-24.04-x64.deb`

Test logs, performance files, unapproved intermediate executables, and CI
metadata remain workflow artifacts and are not attached to the public release.

## Build and validation flow

A dedicated GitHub Actions release workflow runs on Windows and Ubuntu from the
same commit. Pull requests that change release inputs, main-branch pushes, and
manual dispatches all run the build and staging validation, but only a
`push` event for `refs/heads/main` can enter the publication job. Each platform
installs locked dependencies, then runs:

1. Frontend and packaged-E2E type checks
2. The complete frontend test suite
3. Rust formatting, Clippy, and Rust tests with all features
4. Production frontend build
5. Offline/network-boundary audit
6. Platform bundle build
7. Portable-package smoke launch
8. Structural package validation

The Windows job launches the final production
`src-tauri/target/release/prism-pad.exe`, waits ten seconds, requires the process
to remain alive, captures early-exit diagnostics, and always terminates the
process. The Ubuntu job launches the final AppImage itself under `xvfb-run`
with `APPIMAGE_EXTRACT_AND_RUN=1`; only the expected ten-second `timeout`
status is success, and captured logs are printed so an early exit or crash is
diagnosable.

After the smoke launches, the Windows job verifies a non-empty release-profile
portable executable and NSIS installer. The Ubuntu job verifies the Debian
metadata and a non-empty AppImage. Each job copies its two validated sources
into a flat staging directory under the exact public filenames, revalidates
both staged files, and uploads only that directory as a temporary workflow
artifact.

`sha256sum --check` is the fail-closed trust boundary: no helper is made
executable and no bundle starts until all five bytestrings match. Preseeding
the verified cache prevents Tauri bundler 2.9.4 from fetching replacements.

## Publication gate

A final publication job depends on both platform build jobs and requires both
`github.event_name == 'push'` and `github.ref == 'refs/heads/main'`. It merges
the two flat artifacts, confirms that the release-assets root contains exactly
the four approved non-empty filenames, and creates tag and release `v0.1.0`
using GitHub's short-lived workflow token. Pull requests and manual dispatches
therefore stop after validation and cannot mutate a tag or release.

If any check, build, validation, or asset-count assertion fails, the publication
job does not run and no release or tag is created. Tag absence is accepted only
when `git ls-remote` returns status 2, and release absence is accepted only when
the GitHub API returns HTTP 404; transport, authentication, and unexpected API
failures abort publication. If `v0.1.0` already exists, the workflow fails
instead of overwriting it.

Workflow permissions default to `contents: read`; only the publication job
receives `contents: write`. Every external GitHub Action is pinned to an
approved immutable commit SHA.

## Release notes and user expectations

Release notes summarize the editor, supported platforms, syntax/file-extension
behavior, boxed tabs, startup language chooser, local-only privacy boundary,
and key editing features. They explicitly warn that v0.1.0 is unsigned and may
trigger Windows SmartScreen.

## Repository presentation

The README begins with the approved PrismPad document/prism image, centered at
a restrained size. A centered badge row immediately below it shows:

- The live `main` CI/build result
- The latest stable GitHub release
- Windows 10/11 support
- Ubuntu 24.04+ support

The CI and release badges derive their state from GitHub rather than using a
decorative static "stable" claim. Platform badges are informational. No license,
signing, or security badge is shown unless that capability actually exists.

## Trigger and future releases

The v0.1.0 workflow validates release-affecting pull requests before merge, is
triggered again by the merge of its release configuration into `main`, and can
also be started manually for non-publishing validation. Future releases must
update the manifest versions and workflow tag together. They must use a new tag
and may add signing only after the company certificate is stored in GitHub's
protected secret or trusted-signing service.

## Rollback

Because publication is last and immutable, failures before publication require
only a corrective pull request and rerun. If a defect is discovered after
publication, v0.1.0 remains an auditable artifact and a corrected version is
released under a new semantic version; published assets are not silently
replaced.
